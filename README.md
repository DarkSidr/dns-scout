# DNS Scout для OpenWrt

DoH-тестирование с самого роутера и страница **Службы → DNS Scout** в LuCI.
Применение через установленный `https-dns-proxy`. DoT намеренно не поддерживается.

## Возможности

- Проверка настоящего DNS wire-format через HTTPS POST, а не просто ping/HTTP 200.
- Проверка TLS-цепочки и имени сервера, DNS ID, вопроса, RCODE, целостности ответов и наличия публичной A-записи. Редиректы и ответы с частными/sinkhole IP отклоняются.
- Таблица доли успешных ответов, медианы, p95 и конкретной ошибки. Рейтинг: сначала успешность, затем p95; три пробы по умолчанию. При малой выборке p95 близок к максимуму и не доказывает долгосрочную надёжность.
- 18 основных адресов; 94 дополнительных адреса из исторического gist отключены до ручного выбора. Каталог не может охватить «все DNS в интернете»; серверы добавляются вручную, старые удаляются.
- Отдельная таблица bootstrap DNS; настраиваемый список публичных IPv4. Они используются последовательно для разрешения имени HTTPS-сервера. Сам bootstrap — обычный незашифрованный DNS, не резервный транспорт для пользовательских запросов.
- Кнопки теста и применения, редактирование каталога, отдельные флаги «тестировать»/«разрешить выбор».
- Ежедневный cron в заданное время роутера; автоматическое применение включается отдельно. По умолчанию расписание и автоматический выбор выключены.
- До трёх DoH-серверов в порядке приоритета через `dnsmasq strictorder`; известные алиасы одного провайдера не считаются независимыми резервами. Для неизвестных провайдеров группировка по hostname.
- Предварительная проверка кандидатов во временных экземплярах установленного `https-dns-proxy`, затем транзакционное применение с откатом.

## Установка и обновление

Последний релиз из [DarkSidr/dns-scout](https://github.com/DarkSidr/dns-scout):

```sh
curl -fL https://raw.githubusercontent.com/DarkSidr/dns-scout/main/install.sh -o /tmp/dns-scout-install.sh && sh /tmp/dns-scout-install.sh
```

Либо через `wget`:

```sh
wget -O /tmp/dns-scout-install.sh https://raw.githubusercontent.com/DarkSidr/dns-scout/main/install.sh && sh /tmp/dns-scout-install.sh
```

Установщик определяет архитектуру и APK/OPKG, загружает релиз и проверяет SHA256 перед установкой. Настройки сохраняются, переключение DNS и автовыбор не запускаются. Если отсутствуют индексы зависимостей, добавьте `--update-index`. Контрольная сумма проверяет целостность; доверие к автору релиза обеспечивается выбранным HTTPS-источником, а не самой SHA256.

```sh
# Конкретная версия:
sh /tmp/dns-scout-install.sh --version 0.2.0-r1
# Только загрузить/проверить, не устанавливать:
sh /tmp/dns-scout-install.sh --dry-run
# Без доступа к GitHub: каталог с release.json, SHA256SUMS и нужным пакетом:
sh install.sh --local-dir /tmp/dns-scout-release
```

### Ручная установка

Выберите пакет с **точным OpenWrt architecture**, не только похожим процессором.

```sh
# OpenWrt 25.12 (APK), например Banana Pi BPI-R4:
apk add --allow-untrusted /tmp/luci-app-dns-scout-0.2.0-r1.aarch64_cortex-a53.apk

# OpenWrt 23.05 / 24.10 (OPKG):
opkg install /tmp/luci-app-dns-scout_0.2.0-r1_aarch64_cortex-a53.ipk
```

`--allow-untrusted` нужен для локально собранного неподписанного APK. Проверяйте SHA256 из `dist/SHA256SUMS` и устанавливайте только собственную доверенную сборку. Для публичного репозитория нужен собственный ключ подписи.

Зависимости: `luci-base`, `rpcd`, `ca-bundle`, `https-dns-proxy`, штатные `uci`, `ubus`, `dnsmasq`, `cron`. Установка включает восстановление при загрузке и перезапускает rpcd, но **не меняет DNS** и не запускает автоподбор.

Откройте `/cgi-bin/luci/admin/services/dns-scout`; при старом меню обновите страницу браузера. Время расписания берётся из часового пояса роутера. После изменения каталога/параметров нажмите «Сохранить настройки», затем «Запустить тест».

## Выбор основного и резервных DNS

1. Запустите тест.
2. В блоке **Резервные DNS** выберите **Выбрать вручную**.
3. Укажите первый резервный DNS и, при необходимости, второй. «Не использовать» позволяет оставить один резерв или вообще работать без резервов.
4. Нажмите **Сохранить резервирование**. Это сохраняет только предпочтения и ещё не меняет рабочий DNS.
5. Нажмите **Применить** у основного сервера в таблице. Диалог покажет сохранённые резервы; после подтверждения проверяется и применяется вся цепочка.

Основной сервер не должен совпадать с резервным по URL. В ручном режиме резерв должен пройти все тесты: если он недоступен, вся операция отклоняется. Неисправный сервер не заменяется без вашего выбора. Для ручного порядка допускаются разные адреса одного провайдера, но это не обеспечивает независимость провайдеров.

В режиме **Автоматически по рейтингу** остаётся прежнее поведение: параметр «Всего DNS в цепочке» определяет число серверов. При автовыборе по расписанию ручные резервы сохраняются, а основной выбирается из остальных прошедших тест DNS.

Старый файл конфигурации без `fallback_mode` и `fallback_ids` совместим и использует автоматический режим. Сохранение общих настроек также сохраняет текущие настройки резервирования. После несохранённого изменения резервов применение блокируется с понятным сообщением.

## Применение и резервирование

1. Результат должен быть завершённым и не старше часа; применяемый сервер должен пройти все пробы и быть разрешён для выбора.
2. Проверяется отсутствие несохранённых UCI-изменений, одна инстанция dnsmasq на порту 53, `dnsmasq_config_update='*'`, отсутствие глобального внешнего прокси.
3. Кандидаты проверяются **реальной установленной программой https-dns-proxy** на временных loopback-портах. Только после успешной проверки начинается изменение конфигурации.
4. Исходные `/etc/config/https-dns-proxy` и `/etc/config/dhcp` сохраняются в `/etc/dns-scout/transaction/`. Создаётся устойчивый к перезагрузке маркер незавершённой операции и отдельный процесс аварийного восстановления на время транзакции.
5. Старые DoH-инстансы заменяются `scout0…scout2`, слушающими 127.0.0.1:5053–5055. У dnsmasq заменяются общие upstream DNS; адресные правила `/domain/server` сохраняются. Включаются `strictorder`/`noresolv`, отключается `allservers`.
6. Проверяются UCI-порядок, работающие процессы через ubus с нужными URL и портами, DNS-ответы каждого прокси и dnsmasq. Только затем появляется запись о подтверждённом применении.
7. При ошибке конфигурация восстанавливается, службы перезапускаются, показывается результат отката. Если исходный DNS тоже не отвечает, предупреждение и маркер восстановления остаются. После перезагрузки init-скрипт повторяет восстановление.

Запись «последнее подтверждённое применение» — история, а не индикатор непрерывного мониторинга. Доказательство относится к настроенным URL, работающим процессам и локальному DNS-тракту. Оно не является независимой аттестацией владельца рекурсивного сервера.

Резервирование выполняет dnsmasq при ошибках/таймаутах. Оно не заменяет NXDOMAIN или фильтрацию ответа альтернативным провайдером. Переключение может занять время ожидания основного сервера. Тест по расписанию заново ранжирует серверы; постоянного активного health-monitor нет. Если цепочка не изменилась и исправна, повторной записи DNS-настроек и рестартов не происходит.

Откат не восстанавливает работоспособность уже заблокированного прежнего провайдера, но возвращает исходную конфигурацию. Нельзя одновременно менять DNS в другом окне LuCI во время применения: блокировка координирует операции DNS Scout, не сторонние приложения.

## Ресурсы и слабые роутеры

- Нет постоянно работающего демона DNS Scout; cron запускает процесс только в заданное время.
- По умолчанию один тест за раз; максимум восемь. Таймаут 2–15 секунд, 2–10 проб, максимум 300 адресов, ограниченный размер DNS/HTTP-ответа.
- Результаты и прогресс в `/tmp/dns-scout`, не во flash. На flash пишутся настройки и реальные изменения DNS. После перезагрузки таблицу нужно собрать заново.
- У Go-процесса мягкий лимит управляемой памяти 20 MiB и ранний GC. Это **не жёсткий лимит RSS**.
- Измерено на BPI-R4: 18 адресов × 3 запроса, parallel=1, 69 секунд ожидания сети; CPU 0,84 секунды, peak RSS 10 580 KiB. Вызов статуса: примерно 0,01 секунды, peak RSS 6 612 KiB. Это измерения одного устройства, не гарантия для всех архитектур.
- ARM64-бинарник занимает примерно 6 MB; APK около 2,4 MB. Python, Node.js и компилятор на роутере не нужны.
- Для 64/128 MB RAM: parallel=1, 2–3 пробы, короткий список. Дополнительно учитывайте память самого https-dns-proxy, LuCI, VPN и других служб. Для устройств с 32 MB RAM / 4–8 MB flash пригодность не обещается.

Все пробы — холодное соединение: измерение включает bootstrap, TCP/TLS и DNS. Оно отражает доступность при новом подключении, а не установившуюся скорость переиспользуемого HTTPS-соединения. Используется IPv4 к DoH-серверам; IPv6-only адреса не поддерживаются. DNSSEC-валидация самим DNS Scout не выполняется. Быстрый и доступный сервер не обязательно заслуживает доверия и не обязательно обходит фильтрацию.

## Совместимость и сборка

Аппаратно проверена **OpenWrt 25.12.4, BPI-R4, aarch64_cortex-a53**. Пакеты для ARMv7, MIPS, MIPSEL и x86-64 кросс-компилируются; запуск на этих устройствах не проверен. Для 23.05/24.10 подготовлен формат IPK; это не утверждение о проведённых испытаниях на всех старых версиях. Более ранние версии — вне подтверждённого диапазона.

Самостоятельная сборка без SDK-компилятора целевой платформы (Go 1.20+):

```sh
python3 scripts/build-release.py --arch arm64 --openwrt-arch aarch64_cortex-a53
python3 scripts/build-release.py --arch mipsle --openwrt-arch mipsel_24kc
```

Для APK v3 используйте `apk` и **fakeroot из того же OpenWrt SDK**, чтобы корректно записать root-владельцев:

```sh
export STAGING_DIR_HOST=/path/to/openwrt-sdk/staging_dir/host
"$STAGING_DIR_HOST/bin/fakeroot" python3 scripts/build-release.py \
  --arch arm64 --openwrt-arch aarch64_cortex-a53 \
  --apk "$STAGING_DIR_HOST/bin/apk"
```

`Makefile` позволяет включить исходники как `package/dns-scout` в SDK с установленным packages feed и golang/host:

```sh
make menuconfig  # LuCI -> Applications -> luci-app-dns-scout
make package/dns-scout/compile V=s
```

Прямые release-пакеты используют CGO_ENABLED=0, статические бинарники, stripped symbols. Сборка без сторонних Go-модулей. ARMv7-сборка использует GOARM=7, MIPS — softfloat. Обычный SDK Makefile использует правила golang-package соответствующего SDK.

## Проверки

```sh
go test -race ./...
go vet ./...
go test ./... -run '^$' -fuzz FuzzDNSParser -fuzztime=10s
node --check files/www/luci-static/resources/view/services/dns-scout.js
```

Проверяются повреждённые/подменённые DNS-пакеты, compression loops, частные адреса, недоверенный TLS, валидация настроек и расписания, отбраковка устаревших/изменённых кандидатов, ранжирование, независимость резервов и восстановление файлов после частичного сбоя. Фаззинг DNS-парсера: более 860 тысяч входов за отдельный 10-секундный прогон, без ошибок. Сценарии отката используют временные файлы и имитацию системных команд; намеренные сбои рабочего DNS на пользовательском роутере не создавались.

## Диагностика и удаление

```sh
ubus call dns-scout status
ubus call dns-scout scan
# Проверить лидеров через временные прокси, не меняя рабочие DNS:
dns-scout preflight
# Повторить откат незавершённой операции:
dns-scout recover
```

Удаление `apk del luci-app-dns-scout` / `opkg remove luci-app-dns-scout` убирает пакет и его cron-запись. Уже применённые настройки https-dns-proxy остаются рабочими; удаление пакета не переключает DNS назад. При незавершённой транзакции сначала выполните восстановление.

## Версии и выпуск релиза

`VERSION` содержит версию приложения (например, `0.2.0`), `RELEASE` — номер сборки OpenWrt (`1`). Итоговая версия — `0.2.0-r1`; она автоматически попадает в имя пакета, бинарник и `release.json`. Посмотреть установленную версию: `dns-scout version` или заголовок LuCI.

Исходники хранятся в Git; бинарники, локальные сетевые отчёты и снимки интерфейса исключены из истории. Для нового релиза обновите VERSION/RELEASE, CHANGELOG и файл `docs/releases/<версия>-r<сборка>.md`, затем:

```sh
git add .
git commit -m "Release 0.2.0-r1"
git tag -a v0.2.0-r1 -m "DNS Scout 0.2.0-r1"
git push origin main v0.2.0-r1
```

GitHub Actions запускает тесты, собирает пять архитектур в APK/IPK и публикует файлы релиза вместе с SHA256SUMS. Для этого достаточно стандартного GITHUB_TOKEN workflow с правом contents:write; персональный токен в исходниках не нужен. На обычный push/PR запускаются только проверки.
